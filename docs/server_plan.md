本文是把"内容感知超分的语义保真评测"（下称 AdVSR-Bench）在服务器上从头跑完的执行计划：设计修订、阶段步骤、算力与存储、时间表、风险。

## 1. 设计修订（相对 10/02 草案）

定位、四个测试集、按源素材切分、区域级指标为核心、分维度报告、文字幻觉一票否决、人评加专家核查，这些都保留。
需要改的是下面这些，大多数是为了让设计在我们的数据和代码上做得出来、统计上站得住。

### 1.1 任务定义
- **480p 用标准尺寸 854×480 / 480×854**，GT 仍是 1920×1080，各轴缩放比记进 meta.json（2.25 / 2.2482）。现在的 `gt_geometry` 会把 480p 算成 GT 1916×1080，生成直接报错。
  这不是只改一处：`bench/run.py` 的 out_size 和 DOVE `infer.py` 的 --out-short 按缩放比取整，854 宽会输出 1922 宽。合成片段的输出尺寸一律直接取 meta.json 里的 GT 尺寸；
  真实输入取短边 1080、长边按宽高比取最近的偶数（854×480 → 1920×1080，Meta 的 360×450 / 360×360 → 1080×1350 / 1080×1080）。
- **4 秒 = 覆盖 4 秒的最短 8N+1 帧数**（同时满足 SeedVR2 的 4N+1）：30 / 29.97 fps 121 帧，24 / 23.976 fps 97 帧，25 fps 105 帧。测试集保持素材原生帧率，不做帧率转换（50/60 fps 只做 2:1 抽帧）。
  现在的编排会把 25 fps 素材转成 30 fps，v7_test 有 25% 的广告出现重复帧，会污染时序指标，所以测试集要重新生成，不能沿用 v7_test。
- **真实输入的尺寸**：Meta 360p、TikTok 576p（单列一档，约 ×1.875）、YouTube-UGC 360p / 480p。720p 的真实视频不作输入，只作参照。
  真实集按尺寸分层只能报 360 / 480 / 576 三档（没有真实的 270p、540p 来源）；真实广告以竖屏为主（real_ugc_v1 是 34/36），"横竖各半"只对合成集成立。

### 1.3 切分与留出
- 按源视频切分，外加 `data/stats/sources/test_only_sources.csv` 黑名单，生成训练集时拒绝这些源。

- **文案不泄漏**：训练文案只取 calibration / dev 份真实广告，测试文案新写；检查测试品牌名不和训练重名。

### 1.4 退化
- **训练**：按导师要求用 RealBasicVSR 二阶随机退化（H.264 / VP9）。我们的正式参赛模型用纯 RealBasicVSR 参数训练（`rbvsr_prob=1.0`），
  10% 重退化 + 90% 校准的混合作为消融。理由：测试链按真实广告校准，如果训练也用校准参数，我们的模型就是分布内测试，对基线不公平。
- **测试**：四环节串联链（拍摄 → 创作导出 → 平台缩放编码 → 二次转发），用现有算子按固定顺序搭成新预设 `bench`，并配上二次转发环节（概率约 0.2，作为记录的因素）。v6 的转发代码可以移植，在 git abd3e02。
  对导师的说法：这是 Real-ESRGAN 自己的"高阶退化"，只是顺序固定、参数校准。
  Syn-Comp 的 40 条重退化走同一条四环节链，参数取 RealBasicVSR 的范围（文献里的标准设定，多数基线在这部分也是分布内）。
- **两个必须修的问题**：
  - 拍摄端的模糊、噪声现在会作用到后加的文字上（make_pairs 先画字再退化），测试链改成拍摄算子只作用于画面层，文字层之后再合成。
  - GT 和 LQ 没有色彩标签，BT.601 / BT.709 解释不一致会让品牌色偏 ΔE00 1.0–8.7，所有文件都打 bt709 / tv 标签。
    我们自己的 ffmpeg 流程读写用同一个默认矩阵，现有合成集分数自洽；出问题的是解码方式不同的地方：浏览器（人评）、各基线仓库自带的读取代码、带标签的真实文件和无标签输出混比。
- **创作导出只用 H.264**，平台环节按配额选编码；平台环节不加噪声和 JPEG。
- **AV1 只在测试**：用 SVT-AV1（preset 4–6），解码固定用 libdav1d。
- **校准目标 AUC ≤ 0.65 要改用法**：
  - 用像素或 CNN 分类器时，真实广告和我们素材的内容差异本身就能把 AUC 推高，测不出退化像不像，所以判定只用退化统计特征的分类器（像素分类器的结果只报告）。
  - 按现有 W/IQR 换算，这类分类器现在约为 720p 0.71、360p 0.87（360p 主要来自锐化光晕一项，它多半是文字边缘造成的内容差异，去掉后约 0.71）；
    干净对照是 0.84 / 0.95，说明特征确实能识别缺失的退化。所以 0.65 还需要再校准一轮，360p 尤其如此。
  - 真实样本少时置信区间很宽：18 对 18 约 ±0.18，61 对 61 约 ±0.10，200 对 200 约 ±0.05。

  做法：
  - 只用 Real-Cal + Real-Dev；
  - 特征只取亮度上的退化特征，并遮掉文字和人脸区域；
  - GroupKFold 按视频分组，算视频级 AUC 和置信区间；
  - 达标条件：AUC ≤ 0.65、置信区间上界 ≤ 0.72，并且每个单项特征 W/IQR ≤ 0.3（防止靠过度退化来压低 AUC）；
  - 加对照（干净对照、真实对真实）和"同一条广告 Meta 720p→360p"的内容匹配测试；
  - Real-200 冻结，最后只测一次并报告。
- **发布**：测试 LQ 的最后一步必须是编码，直接发布原生码流（H.264 .mp4、VP9 .webm、AV1 .mp4），去掉 x264 的 SEI，附 sha256 和解码帧的 framemd5。
  编码器在不同线程数下产出的码流不同，所以只能发布码流，不能只发种子。测试数据总量约 3.5 GB（GT 用 CRF 10 约 12.7 MB / 条，4 个尺寸的 LQ 码流约 1 MB / 条），另加 mask。

### 1.5 指标
- **全局**：LPIPS、DISTS 用于排序；PSNR / SSIM 只报告。
- **无参考**：DOVER、MUSIQ、Q-Align、COVER 只作辅助；在合成集上同时报告"输出得分减 GT 得分"和"输出高于自身 GT 的比例"，作为过度锐化的直接证据。
- **时序**：E*warp 在 GT 上用 RAFT 算光流，遮挡用前后一致性掩掉，切换附近两帧不算，报告和 GT 的差值；真实集用自身光流的版本。只和 LPIPS 并列展示，不单独排序。
- **LR 一致性**：输出和 LQ 都先缩到 LQ 尺寸，再做 σ=1 像素的低通后比较。只作幻觉闸门，不排序，因为什么都不做的方法分数最好。
- **文字**（核心）：
  - 以单词为单位。两个结构不同的 OCR：PP-OCRv5 和 PARSeq，EasyOCR 只为和 v7 结果衔接；不用 TrOCR，它会自动纠正拼写，把幻觉"读对"。
    PARSeq 默认是自回归解码加迭代修正，内部也有语言模型，同样会纠正，所以用非自回归模式、refine_iters=0（或换第二个 CTC 识别器），并用"只改一个字"的正样本确认两个引擎都不纠正。
  - 两个引擎都能读对 GT 的单词才进入统计；NED 用 ICDAR 定义，范围 0–1。
  - 笔画级保真：用合成器导出的纯字形 mask 算笔画 F1 和边缘 F1，允许 ±2 px 对齐。
  - 幻觉 = 两个引擎都读错，且看起来清晰：置信度 ≥ τ_c，且字形区域梯度能量与 GT 之比 ≥ τ_s。
  - 阈值用三名专家的标注拟合（逐个留出一个系统做交叉验证），并加"只改一个数字重新渲染"的正样本做对照。
  - 按 LQ 上的字号分档报告；数字类（价格、优惠码）单独报告完全匹配率。
- **红线**：和 bicubic 在同一批单词上比，幻觉率高出 ≥2 个百分点且片段级自助法置信区间不含 0，就标红；Lite-120 上专家确认改错的数字比例 ≥1% 也标红。
- **logo / 商品**：
  - 我们的 logo 是字体渲染的文字，用文字指标加 ΔE00（取字形或底板 mask 内的 Lab 中位数）。
  - 商品用 DINOv2 ViT-B/14-reg 的对齐 patch token 余弦相似度。框的来源：合成器导出的卡片照片框；素材里的商品用 OWLv2 + SAM 2 自动框出再人工核对。
- **人脸**：YuNet 检测，ArcFace 和 SFace 并列报告。insightface 的 ArcFace 权重仅限非商用；OpenCV 的 SFace 文件是 Apache-2.0，
  但训练用了 CASIA-WebFace、VGGFace2、MS-Celeb-1M，可否商用同样要法务确认，而且它是 MobileFaceNet，区分力弱一些。两张脸都用 GT 的关键点对齐。按 LQ 像素里的脸高分档：<16、16–32、32–64、≥64。
- **真实集的区域指标**：人工从 720p 参照（没有参照就从 LQ）转写文字并画框，约 600 个单元；LQ 上看不清、输出却清楚读出的文字交给专家判断（多帧方法确实可能恢复出来）。
- **标注和评分用不同的 OCR**：Syn-Nat、Real-200 的文字标注用 EasyOCR 预填、人工逐条核对；评分用的 PP-OCRv5 和 PARSeq 不参与标注，避免同一个引擎既出答案又打分，抬高闸门通过率。
- **统计**：每个维度事先指定一个主指标（全局 LPIPS、文字幻觉率、logo ΔE00、商品 DINOv2、人脸身份相似度、时序 E*warp 差值），和红线一起在 OSF 预注册；
  区间用按片段聚类的自助法，多重比较用 Holm 校正；按尺寸、编码、字号等的分层结果只作探索性报告。
- **评测输出**：
  - 存成 yuv444p 或在进程内直接算，避免 4:2:0 损伤细笔画的颜色；
  - 每个单词、每张脸、每个商品各记一行（parquet 长表），自助法和阈值拟合都要用到。

### 1.6 基线与效率
- 方法清单冻结在 `configs/bench/methods.yaml`（代码版本、权重哈希、模式、精度）。按成本分三档：
  - **A 档**（全部输入）：Bicubic、Real-ESRGAN、BasicVSR++、RealBasicVSR、FlashVSR v1.1（Full + Tiny）、DOVE、我们的模型。
  - **B 档**（核心子集：每条 GT 一个尺寸 + Real-200）：SeedVR2-3B、SeedVR2-7B、SparkVSR（pisasr 模式）。
  - **C 档**：STAR 跑 Lite-120；Upscale-A-Video、MGLD-VSR 只跑 Lite 的 60 条合成（两者不在人评的 8 个系统里，所以没有真实集分数；预算有余再补真实那一半）。
  - **可选**：DLoRAL、Vivid-VR（自带 OCR 修字，开 / 关都报告）、VEnhancer、RealViformer。
  - 跨档比较只在共同覆盖的子集上做；每档的红线按各自覆盖的单词计算并注明覆盖范围。
- **运行模式**：固定 ×4 结构的模型按原生 ×4 跑再 area 缩到 GT 尺寸。Upscale-A-Video 也是固定 ×4，540p 输入要在 2160×3840 上跑，计算量是 1080p 的 4 倍。
  内部先放大的模型（DOVE、SparkVSR、SeedVR2、FlashVSR）直接在 GT 尺寸上跑，按各自要求补边、补帧到 8N+1 或 4N+1，再裁回。
  SparkVSR 已支持 `--output_resolution H W`，适配器还要改掉它的默认 `--fps 16` 和 `--save_format yuv444p`。
- **统一写出**：所有适配器把原始帧交给同一个写出器（无损或 CRF ≤10、原生帧率、bt709 / tv 标签），不用各仓库自带的保存代码
  （FlashVSR v1.1 用 imageio quality=6 有损保存，还把 23.976 fps 取整成 24）。
- **统一切点**：每个视频方法都吃同一份镜头切点（`--cuts`）：合成片段用 GT 的切点和转场，真实片段用一次冻结的检测结果。
  现在只有 DOVE 分镜头，而且是在退化后的 LQ 上用 PySceneDetect 检测；加单元测试，确认合成器的叠化转场不会被跨镜头修复。
- **时间窗口**：DOVE、SparkVSR、SeedVR2 这类全注意力模型，每次处理的帧数越多，每帧耗时越高。每个方法的窗口长度和重叠固定写进 methods.yaml，质量和效率两次运行用同一设置。
  我们的 DOVE 包装一次最多处理 129 帧，4 秒片段不切块、没有重叠开销，只有补到 8N+1 的那几帧。
- **可复现**：每条输出的记录里写方法配置哈希、输入 sha256、种子、TF32 / cuDNN 设置，续跑时不一致就拒绝复用旧输出；在 Lite 子集上报告重复运行的波动。
- **效率**：
  - 硬件：单张 A100-80GB；
  - 计时：预热 1 条，3 次重复取中位数，用 CUDA 事件计时；模型加载、解码、编码不计入但单独计时；
  - 显存：报告 allocated、reserved、NVML 三种峰值；
  - 额外报告：重方法另报"24 GB 显存模式"一行；处理一分钟广告的 GPU 秒数，用一条真实 60 秒广告端到端实测（含切换、补帧、重叠的开销）。
- **算力**：按草案原样跑约 1,160 A100·h（推理约 760，训练与消融约 180，指标约 80，其余约 140）；分档后推理约 470、合计约 830。
  比上一版估计（1,020 / 750）多出的部分有两项：Upscale-A-Video 的 ×4 修正（Lite 合成部分从 36 升到约 89 A100·h），以及编码配对子集多出的 80 个输入（约 26 A100·h）。
  750 是硬上限时：MGLD-VSR 改为可选（−60），Upscale-A-Video 只跑 ≤360p 的 30 条 Lite 片段（−64），合计约 710。
  先花 20–30 A100·h 实测速度，再定最终分档。

### 1.7 人评
- **众包两两比较**：在 Lite-120 上比较 8 个系统：Bicubic、RealBasicVSR、FlashVSR、DOVE、SeedVR2-7B、SparkVSR、STAR、我们的模型。GT 和 Meta 720p 只出现在检验题里。
  - **票数**：第一阶段每个"片段 × 系统对"一票（3,360 票）；第二阶段约 850 票，用于复投和在置信区间重叠的系统对上加票（ASAP）。另加约 10% 的检验题，共约 4,600 次评判、30–38 评分人小时。
    草案的"每对 10 票"是 33,600 票、约 210 评分人小时、Prolific 上 3,400–4,500 美元。加票能换来多少精度取决于系统在不同片段间的波动（模拟里 10 倍票数换 1.7 倍到 3.1 倍），这个波动还没测过，所以第二阶段的票数等试点估出它再定。
  - **评分人**：预计招 60 人，至少 35 名有效；用 Prolific 约 600–900 美元，先申请 TAMU IRB 豁免。
    ITU-T P.910 要求非受控环境下每个刺激至少由 35 人评过，稀疏两两比较做不到，属于偏离，论文里如实写明，由合并的 Bradley-Terry 模型汇总。
  - **检验题**：G1 画质（GT 对比 270p bicubic）、G2 文字（同一广告把大标题故意改坏）、G3 重复（换边重放）。排除规则事先写定。
  - **观看**：所有设备都用 A/B 切换模式，有效缩放 ≥0.75，否则按区域裁窗；每票记录屏幕、设备像素比和缩放。现在电脑并排模式在普通屏幕上只显示到 0.31 倍（高分屏约 0.61 倍）。
  - **统计**：混合效应 Bradley-Terry 模型（片段 × 系统、评分人 × 系统两类随机效应，加左右偏好项），差距不显著的系统归为同一档。
  - **工具要改**：加检验题和排除规则；按会话发题；英文界面；同意书；Prolific 对接；视频改用 nginx 提供（支持分段请求，否则 iPhone 播不了）并转成 4 秒的分发版本；
    分发版本统一打 bt709 / tv 标签，用色卡片段在 iPhone Safari、安卓 Chrome、电脑上核对（现在方法输出无标签，Meta 720p 参照有标签，浏览器里两者会有色差）；
    分析改用按评分人和片段聚类的自助法（现在是逐票独立重采样，区间约窄一半）。
  - **众包只问偏好**，外加一个"文字难读或变形"的可选标记。是否被改错由专家判断，因为没有参照时人看不出改错，无参考的偏好还会偏向清晰的错字。
- **专家核查**：
  - 3 名专家按区域逐个看：参照裁剪、输出裁剪、LQ 裁剪，各放大 2 倍同步循环播放；
  - 标签：正确 / 看不清 / 被改 / 清晰但无从核实 / 无法判断，外加错误类型标签；
  - 先校准到 Fleiss κ ≥ 0.6，再正式标注；bicubic 当负对照，约 5% 人为注入的改动当正对照；
  - 工作量：每人约 7–10 小时；
  - 真实视频没有参照时，先转写、再看输出。
- **指标验证**：
  - 主要看逐对准确率：在 3,360 个片段对上，指标偏好的输出和那一票一致的比例。每对只有一票，所以它估计的是"和随机一名评分人一致的概率"；
    上限用复投片段对上评分人之间的一致率来估，平局校准也只在复投子集上做；
  - 区域指标看对专家标签的 AUROC；
  - 系统级相关只作参考：8 个系统时 Spearman 要 ≥0.738 才显著。

1. 抓 Meta 广告库约 300 条同时带 360p 和 720p 的新广告（投放地选欧盟，广告会保留一年），以及 TikTok 约 60 条 576p 广告：`adup.real_ads.meta_adlib_web`、`adup.real_ads.tiktok_topads`。

### 阶段 4：退化校准（第 2–3 周）
1. 用 dev 份素材编排约 200 条广告，按 `bench` 预设生成 360p 和 720p，加干净对照；跑 `degradation_stats`、`quality`、`compare` 得到 W/IQR。
2. `realism_c2st.py`：按 1.4 节的协议算分类器 AUC，跑对照和"Meta 720p→360p"内容匹配测试。最多调 3 轮参数，之后冻结配置、git 哈希和种子。
3. AV1 码率：按平台比例换算各档 bpp，用 YouTube 格式列表核对（只读码率，不下视频）。

### 阶段 5：冻结测试集（第 3 周，CPU）
1. 生成 Syn-Comp（160 × 4 尺寸 + 编码配对子集）、Syn-Nat（80 × 4），用 `--shard` 并行。单进程约 4–5 小时，峰值约 6 GB / 进程。
2. 校验每个 LQ：ffprobe 的编码、帧数和 GT 一致；固定解码器求 framemd5；换一台机器或另一个 ffmpeg 版本重解码，结果必须一致。按固定流程解码成 PNG，所有方法吃同样的帧。
3. 标注：合成器元数据，加 OCR / 人脸 / 商品自动框，再人工核对（约 27 标注人时）。文字预填只用 EasyOCR，不用评分用的两个引擎（见 1.5）。
4. 抽 Lite-120（固定种子，写 `lite120.csv`），整体写 sha256 清单。
5. 按许可分层打包：
   - 公开：UltraVideo 衍生（CC BY-NC 4.0）、YouTube-UGC、ABO、OFL 字体；
   - 内部：KwaiVIR、Unsplash；
   - 隐藏测试：真实广告只发 id、时间码和哈希。

### 阶段 6：训练数据（第 3 周，CPU）
1. 约 5,000 条训练广告 × 2 个 LQ（可放宽到全部现有素材的上限），用 RealBasicVSR 参数（主模型）和 10% 混合（消融）各生成一份。
   训练 LQ 也改存原生码流，体积从每条约 28 MB 降到 1 MB 以下。
2. 约 2,400 张广告风格图片 × 2–3 个 LQ（Unsplash 照片叠字、App 界面、少量普通照片）。
3. 用 `adup.batch` 在多核上并行。按每条 26 秒（单进程）估算，5,000 条约 36 进程小时，64 核机器上约 6–8 小时。

### 阶段 7：基线（第 3–5 周，GPU）
1. 每个方法一个环境：mmagic（BasicVSR++、RealBasicVSR）、FlashVSR（DiffSynth + Block-Sparse-Attention，编译时限制并行数）、SeedVR2、SparkVSR（沿用 DOVE 的 diffusers 环境）、STAR（I2VGen-XL）、Upscale-A-Video、MGLD-VSR。
   权重直接从 HF / Google Drive 下到服务器，约 150–200 GB。
2. 冒烟测试（约 3 A100·h）：3 条片段（竖屏、横屏、多镜头）× 每个方法。检查尺寸、帧数、帧率一致，和 bicubic 无亚像素位移，色域正常。
3. 效率实测（约 20–30 A100·h，必须在 A100 上；服务器没有 A100 就只为这一项租一张）：写 `outputs/bench/efficiency/a100.csv`，重算预算，定分档。
4. 按档运行：`python -m adup.bench.run --method <m> --pairs <集合> --out outputs/bench/<集合>`。每张 GPU 一个队列，已完成的自动跳过。
   A 档约 160、B 档约 100、C 档约 210 A100·h。每周对照预算，超支 10% 以上时先砍 C 档（先 MGLD，再 Upscale-A-Video）。

### 阶段 8：微调 DOVE（第 4–5 周，4×80 GB）
1. 改数据加载：读配对的 GT 和 LQ，只读需要的帧窗口，修 DOVE 官方的 IndexError（issue #20，图片少于视频时崩溃），只加载当步用到的分支。
2. 主训练：从官方权重继续（第一阶段续训 + 第二阶段 500 步），约 80 A100·h。
3. 消融：每个约 15 A100·h，只在 dev 上评测，各约 5 A100·h。内容包括：
   - 重退化比例：1.0 对比 0.1；
   - 图片比例：0.2、0.5、0.8；
   - 训练是否加 AV1；
   - 是否加文字 mask 加权损失。
4. 最终模型跑全部 A 档输入（约 58 A100·h）。

### 阶段 9：评测与报告（第 5–6 周）
1. GT 侧预计算，每条只做一次：双 OCR、人脸轨迹、商品框、RAFT 光流、无参考分。然后所有方法一起算，约 70–80 A100·h。
2. 先在 v7_dev 上用 bicubic、Real-ESRGAN、DOVE 试跑新评测，测 OCR 闸门的保留率、bicubic 的幻觉率下限和正样本召回。
3. 每个维度一张表（全局、时序、文字、logo / 商品、人脸、无参考、成本），带片段自助法 95% 区间和红线，按尺寸、编码、字号、脸大小、见过 / 没见过的字体分层。

### 阶段 10：人评（IRB 第 0 周提交，研究在第 4–8 周）
1. 第 0 周：导师作为 PI 提交 TAMU IRB 豁免申请，相关人员完成 CITI 培训，开 Prolific 学术账户。
2. 工具 v2 完成后，部署到一台小型公网服务器：nginx + HTTPS + 分段请求 + 签名链接。用 iPhone Safari、安卓 Chrome、电脑分别测试。
3. 试点：10 名 Prolific 评分人 + 3 名实验室成员，各做一个 60 题会话。用试点结果估出系统在片段间的波动、重估所需票数，然后在 OSF 预注册排除规则、模型、各维度主指标和红线。
4. 正式：第一阶段 3,360 + 检验题，约 62 个会话；第二阶段约 850 票，约 16 个会话。每天看质控面板。
5. 专家：写指南、校准到 κ ≥ 0.6，再按区域正式标注，每人约 7–10 小时。
6. 分析：BT 分档、专家改错率、偏好与保真的对比（这是论文的核心结果之一）、指标验证。

### 阶段 11：发布（第 8 周起）
发布测试集分层包、方法配置、评测代码、人评设计和投票（评分人 id 哈希化）、专家标签、排行榜；真实广告部分做成隐藏测试。

## 3. 算力与存储预算

| 项目 | A100·h（分档后） | 按草案原样 |
|---|---|---|
| 推理：A 档 / B 档 / C 档 | 162 / 100 / 209 | 约 760（全部方法全覆盖） |
| 微调主训练 + 消融 | 80 + 约 100 | 同 |
| 指标 | 约 70 | 约 80 |
| 退化校准分类器 | 约 20 | 同 |
| 效率实测 | 约 30 | 同 |
| 重跑余量 | 约 60 | 约 90 |
| **合计** | **约 830**（740–1,100） | **约 1,160**（1,030–1,570） |

括号里是按各方法速度的低 / 高估计算出的推理范围，其余项不变。推理已含 Upscale-A-Video 的 ×4 修正和编码配对子集；规划速度取自 FlashVSR、DOVE、DLoRAL 论文的 A100 表和本机 DOVE 实测。

| 存储 | 大小 |
|---|---|
| 素材（现有 38 GB + UltraVideo 36 GB + OpenVidHD 约 20 GB + YouTube-UGC / ABO / Unsplash 约 30 GB） | 约 125 GB |
| 训练配对（5,000 条，LQ 存码流）+ 图片 | 约 70–90 GB |

## 5. 风险与对策
| 风险 | 对策 |
|---|---|
| 服务器不能上网 | 本地经 hf-mirror 直连下载（不耗代理流量），再传到服务器；需要代理的（Meta、TikTok、YouTube、Google Drive）找能上网的机器 |
| 没有 A100 | 只为效率表租一张 A100-80GB 约 30 小时，其余在现有 GPU 上跑 |
| 校准 AUC 达不到 0.65 | 以"单项 W/IQR ≤ 0.3 + 对照"为主，AUC 如实报告；不靠过度退化压分 |
| 美妆、保健素材不够 | 测试集按区域内容分层而不是按主题；训练集用 OpenVidHD 横屏 + 照片补；必要时找创作者拍摄 |
| 人评招不到人或 IRB 拖延 | 先用实验室外的志愿者（≥24 人，受控环境），众包作为扩展 |
| SparkVSR 等基线在 1080p 上显存不够 | 用官方的分块 / 时间切块 / 卸载模式，并在效率表里单独标注 |
| 许可限制发布 | 公开、内部、隐藏测试三层；真实广告部分走评测服务器 |
